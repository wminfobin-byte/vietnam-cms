3 계약요청 · 계약승인 신규

3-1 결제

계약승인 처리 페이지 신설

상담원이 접수(COD)한 건은 계약요청 상태가 되고, 승인권자가 3-1 결제 화면에서 계약승인해야 배송대기로 진행됨. 승인 전 건은 3-4 배송 목록에 나타나지 않음.

용어 — 결제가 아니라 구매 베트남은 COD(대금상환)라 이 시점에 실제 결제가 일어나지 않음. 그래서 계약요청 · 계약승인으로 부름.
현재 화면 없음 — 신규 개발 현행 CMS에는 승인 단계 자체가 없어 접수 후 곧바로 배송대기로 넘어감. 계약승인 처리 페이지(3-1 결제)를 신설해 승인 게이트를 만들어야 함.
  1. 계약요청 생성 — 1-2 고객상담 > [상담] > COD 접수 저장 시 상담상태 할부_현금(COD) / 구매_현금(COD) · 고객상태 계약요청.
  2. 계약승인 목록 (3-1 결제) — 고객상태 계약요청인 건 목록. 컬럼: 번호 · 고객명 · 주문키 · 제품 · 결제방식(할부/구매) · 결제금액 · 현재 상태. 다중 선택 → [선택 건 계약승인].
  3. 승인 결과 — 고객상태 배송대기로 전환. 이때부터 3-4 배송 목록에 노출됨.
  4. 권한 — 관리자관리 · 관리자 · 매니저아웃바운드매니저 · 재무담당자재무 · 관리자.

계약 반려 신규

  1. 3-1 목록 행마다 [반려] 버튼. 클릭 시 반려 사유(드롭다운) + 상세 내용(텍스트)을 입력받음.
  2. 사유 선택지(안) — 고객 변심 · 재확인 필요 / 결제금액 · 할부조건 오류 / 주소 · 연락처 불명확 / 신분증 정보 미비 / 중복 접수 / 기타.
  3. 반려 결과 — 고객상태를 접수 이전(상담대기)으로 되돌리고, 상담상태에 계약반려를 기록. 상담원이 내용을 보완해 다시 접수할 수 있음.
  4. 별도 계약반려 고객상태는 두지 않음 — 상태값을 늘리지 않고 상담상태 + 이력으로 구분(2번 상태값 최소화 원칙).
  5. 반려 이력은 고객 히스토리에 [일시 · 처리자 · 계약 반려] 사유 — 상세로 기록.
  6. 권한 — 계약승인과 동일(관리자 · 매니저 · 재무담당자).
상태전이 상담대기 → 계약요청 → (3-1 계약승인) → 배송대기

4 배송처리 · 계약서 출력 개선

3-4 배송

배송처리 시 계약서 개별 출력 · ZIP 일괄 다운로드

배송처리하는 시점에 해당 고객의 계약서를 함께 뽑아 동봉해야 함. 건별로 하나씩 출력하는 것과, 배송처리한 건 전체를 ZIP 한 파일로 내려받는 것 두 가지가 모두 필요.

  1. 주문키 — DB가 생성되는 시점에 건마다 이미 발급되어 있고, 3-4 배송처리 화면에서 목록에 함께 노출됨. 4-6 시리얼 업로드의 매칭 키, 계약서 계약번호(Số), 계약서 ZIP 파일명에 모두 이 값을 씀. 접수 이전 단계에도 값이 존재하므로 계약서 출력 시점에 제약이 없음.
  2. 목록 — 고객상태 배송대기(=계약승인 완료) 건. 컬럼: 선택 · 번호 · 고객명 · 주문키 · 제품 · 결제 · 현재 상태 · 계약서.
  3. ① 개별 출력 — 행별 [계약서] 버튼. 클릭 시 그 고객 계약서 1건을 PDF로 출력(인쇄창). 양식·매핑은 19번 계약서 출력 · 양식 매핑과 동일.
  4. ② 일괄 ZIP — 다중 선택 후 [선택 건 배송처리] 시 선택한 고객의 계약서 PDF 전체를 ZIP 파일 하나로 다운로드하고, 고객상태를 배송중으로 전환.
  5. ZIP 내부 파일명 — [WM Viet Nam]HỢP ĐỒNG MUA BÁN_{주문키}.pdf (1건 = 1파일). ZIP 파일명은 계약서_{YYYYMMDD}_{건수}건.zip.
  6. 권한 — 배송처리: 물류 · 매니저 · 관리자아웃바운드매니저 / 관리 · 관리자 / 계약서 출력 · ZIP: 관리자 · 매니저만(물류 제외).
배송처리만 하고 계약서는 받지 않을 수도 있어야 하므로 [선택 건 계약서 ZIP만 받기] 버튼을 별도로 둠(상태 전이 없음). 물류가 배송처리하면 ZIP 없이 상태만 전이되고, 계약서는 관리자·매니저가 이 버튼으로 따로 받음.
직인 · 서명은 이미지로 넣지 않음 — 실물 날인이 법적 요건 베트남 법상 계약서에 실물 직인을 직접 날인해야 하므로, 직인 · 서명 이미지를 PDF에 합성하지 않음. 계약서는 직인란 · 서명란을 비운 채 출력하고, 출력물에 건건이 실물 도장을 찍은 뒤 배송에 동봉함. 고객(BÊN B) 서명은 현장에서 수기로 받음.
※ 따라서 ZIP 일괄 다운로드로 뽑아도 날인은 건수만큼 수작업으로 남음. 시스템이 줄여주는 것은 출력 · 취합 단계까지임.
상태전이 배송대기 → (3-4 배송처리 + 계약서 ZIP) → 배송중

5 계약완료 처리 — 시리얼 업로드 / 입금처리

4-6 · 3-9 · 3-10

계약완료 = ① 시리얼 업로드 + ② 입금처리

계약완료는 ① 시리얼번호 등록(출고 단말기 확정)과 ② 입금처리(선납금 확인)가 모두 완료되어야 성립. 둘 다 완료되면 계약완료가 되고, 그 시점부터 해지 접수 가능.

4-6은 시리얼번호 업로드 메뉴명은 4-6 시리얼번호 업로드, 업로드 양식 컬럼은 주문키 · 시리얼 2열뿐. 그 외 컬럼은 두지 않음.
현재 화면 없음 — 신규 개발 시리얼 업로드 · 입금처리 · 계약완료 화면이 베트남 CMS에 존재하지 않음.
  1. ① 시리얼번호 업로드 (4-6) — 시리얼 미등록 건 목록 → 행별 시리얼번호 입력 후 행마다 [시리얼확인] 개별 처리 또는 체크 후 다중 선택 일괄 처리. 그 외 엑셀 업로드(주문키 | 시리얼 2열) · 수기 등록(주문키 + 시리얼). 노출: 물류 · 관리자아웃바운드매니저 / 관리 · 관리자.
  2. ② 입금처리 (3-9) — 입금 미확인 건 목록 → 행별 입금액 입력 후 행마다 [입금확인] 개별 처리 또는 체크 후 다중 선택 일괄 처리. 가상계좌 연동은 10번(후속 개발) — 1차는 수기 확인. 노출: 재무담당자재무 · 관리자.
  3. 시리얼은 마지막 등록만 유효 추가 — 같은 시리얼번호가 이미 다른 고객에게 등록돼 있으면, 저장을 막지 않고 직전 고객의 시리얼을 자동으로 해제한 뒤 새로 등록한 쪽에만 남김.
    • 해제된 건은 시리얼 미등록 상태로 되돌아가 4-6 목록에 다시 나타나고, 계약완료도 함께 해제됨.
    • 해제 사실을 양쪽 고객 히스토리에 기록하고, 처리 결과 토스트에 "중복 n건 직전 등록 자동 해제"로 표시.
    • 비교는 S/N: 접두어와 대소문자를 무시하고 수행(S/N: R83X… · S/N:R83X… · R83X…를 같은 값으로 봄).
    이렇게 하면 기존 데이터의 시리얼 중복도 적재를 막지 않고, 결과적으로 시리얼 1개 = 고객 1명이 보장되어 8번 기기반납 확인 판정이 성립함.
  4. 엑셀 재업로드 방지 추가 — 같은 파일을 두 번 올려도 중복 반영되지 않도록 업로드 이력(파일명 · 행 키 · 처리일시)을 남기고, 이미 처리된 키는 건너뛴 뒤 결과에 "미반영 n건(중복)"으로 표시.
  5. ③ 계약완료 처리 (3-10) — 시리얼 + 입금이 모두 완료된 건은 자동 계약완료. 3-10은 자동 처리가 누락된 건을 수동 확정하는 백업 화면. 노출: 관리자관리 · 관리자.
①②는 처리 순서 무관(독립). 고객상태는 배송대기 → 배송중(3-4) → 계약완료(3-10)만 사용하고, 시리얼 등록 여부와 입금 여부는 고객상태가 아니라 별도 플래그로 관리함.
시리얼번호의 쓰임 ⓐ 1-2 상담창에 시리얼 표시 ⓑ 20번 기기 PW 발송 조회 키 ⓒ 8번 해지대기에서 기기반납 확인 키. 세 곳이 같은 값을 쓰므로 4-6에서 반드시 등록되어야 함.
시리얼 등록일 = 배송완료일 4-6에서 시리얼번호를 등록한 날이 곧 배송완료일이며, 해지 위약금 산정의 기준일이 됨. 따라서 시리얼 등록일을 별도 컬럼으로 저장해야 함(등록 시각 자동 기록, 수정 시 이력 남김).

6 취소 접수

1-2 고객상담 > [상담]

취소 접수 (배송 전/후)

배송대기 · 배송중 상태의 건을 상담원이 취소로 전환. 배송전취소와 배송후 수취거절을 동일하게 처리.

워딩 규칙 — 접수는 두 가지뿐 계약완료 전에 되돌리는 것은 「취소 접수」, 계약완료 후에 계약을 끝내는 것은 「해지 접수」. 화면·상담상태·이력 문구를 전부 이 두 워딩으로 통일. 반품접수 · 중도해지 표현은 쓰지 않음.
환불 단계 없음 취소 접수 → 취소 승인 → 취소로 끝남. 베트남은 COD(대금상환)라 배송 전 취소·수취거절 시점에는 고객이 지불한 금액이 없어 환불 자체가 발생하지 않음.

취소 접수뿐 아니라 해지 접수 · 위약금 협의 등 관련 처리는 모두 상담창의 상담상태 선택(대분류→소분류) + 이력 작성 방식으로 처리 (국내 CMS 동일). 아래는 국내 상담상태 선택 화면.

대분류 이름 — 반품 → 취소 · 해지 6번에서 "반품접수·중도해지 표현은 쓰지 않는다"고 정해 놓고 대분류만 반품으로 남아 있어 앞뒤가 맞지 않았음. 소분류가 전부 취소 접수 · 해지 접수 · 위약금 협의라 취소 · 해지로 통일함. 베트남어 표기 Hủy · Chấm dứt HĐ.
※ 베트남은 실제로 물건을 되돌려받는 "반품" 절차가 없고(COD·환불 없음), 되돌리는 경로가 취소와 해지 둘뿐이라 이름이 곧 프로세스와 일치함.
  • 대분류 취소 · 해지 선택 시 소분류로 상황별 처리 노출: 취소 접수 - 배송전취소 · 취소 접수 - 배송후 수취거절 · 해지 접수 · 위약금 협의·수정.
  • 소분류는 현재 고객상태 + 로그인 사용자의 (팀, 타입)에 따라 가능한 것만 노출 — 예: 위약금 협의=미납담당자재무 · 아웃바운드(매니저). 전체 조건은 11번 참조.
  • 저장 시 상담 이력에 누적 기록 (일시 · 담당자 · 대분류>소분류 · 내용).
  1. 취소 접수 — 고객상태 배송대기/배송중 건에서 상담상태 취소 · 해지 > 취소 접수(배송전취소 / 배송후 수취거절) 선택 → 고객상태 취소접수 + 이력. (상담원)
  2. 취소 승인 — 1-2 DB 리스트 기능 컬럼의 [취소 승인] 버튼. 매니저타입 아웃바운드매니저 · 관리자에게만 노출. 클릭 시 고객상태 취소로 종결. 별도 환불 화면 없음.
반송 단말기 회수는 별도로 관리하지 않음 배송후 수취거절 건도 [취소 승인] 한 번으로 종결하며, 반송 단말기 회수 확인을 위한 별도 상태나 시리얼 입력 단계를 두지 않음.
상태전이 배송대기/배송중 → 취소접수 → (매니저 취소 승인) → 취소

7 해지 접수 · 해지취소 버튼

1-2 DB 리스트 / 상담창

해지 접수 + [해지취소] 버튼 노출

계약완료 건을 해지 접수로 전환. 접수 시점에는 위약금 결제인지 기기 반납인지 고르지 않고, 위약금 산정만 하고 접수함.

접수 시 반품방식 선택 없음 해지 접수는 위약금이니 기기반납이니 선택 없이 진행하고, 실제 해지를 확정하는 시점(8번 해지대기)에 기기반납 / 위약금결제가 결정됨. 따라서 접수 상태값은 해지대기 하나뿐이고, 위약금 미입금 · 위약금 협의 · 위약금 입금 · 입고대기 · 반품입고 같은 세분화 상태값은 두지 않음.
용어 주의 — [해지취소] = 해지 철회 이 버튼은 "해지를 시작"하는 버튼이 아님. 해지 접수까지 진행한 건에서 고객이 "그냥 사용하겠다"고 할 때 해지를 철회해 다시 계약완료로 되돌리는 버튼임.
  1. 해지 접수 시작은 상담창에서 선택 — 상담상태 취소 · 해지 대분류 > 해지 접수 소분류 선택(6번 상담창 방식). 선택 시 해지 접수창(9번, 국내 반품접수창 기반)이 상담창 안에 인라인으로 열림.
  2. 접수창에서 하는 일 — 고객·계약 정보 확인 → 위약금 산정 기준일 → 위약금 산정(최초 산정 · 조정(할인) · 최종) → 안내 확인 → 저장. 반품방식 선택 · 수거방식 선택 UI는 두지 않음.
  3. 저장 결과 — 고객상태 해지대기. 접수와 동시에 8번 3-6 해지대기 목록에 올라가며, 접수 직후의 별도 승인 단계는 없음. 승인은 3-6에서 종결과 함께 이뤄짐.
  4. [해지취소] 버튼(철회)은 해지대기 구간에 노출팀 무관 · 타입 아웃바운드매니저 — 매니저·관리자 계정에만 표시. 클릭 시 확인 후 계약완료로 복귀(이력 기록).
처리 위치 해지 최종 처리(위약금 입금 확인 / 기기반납 확인)는 3-6 해지대기에서 진행. 따라서 1-2 기능 컬럼에는 [상담] · [취소 승인] · [해지취소(철회)] · [고객 관리]만 둠.
상태전이 계약완료 → 해지대기 → (3-6 해지 승인) → 해지(위약금) / 해지(기기반납)

8 해지대기 — 해지 처리 신규 메뉴

3-6 해지대기

위약금 입금 / 기기반납 확인 후 해지 종결

해지 접수된 해지대기 건을 개별로 해지 승인해 종결시키는 화면. 해지 흐름의 마지막 단계이며, 3-6 메뉴는 이 화면으로 씀.

위약금 산식 — 확정 상세는 9-1. 위약금 산정 규칙 참조. 요약: 배송완료(=시리얼 등록) 14일 이내 4.000.000 ₫ / 14일 초과 5.000.000 ₫, 여기서 고객이 이미 낸 돈을 뺀 금액만 청구. 기기반납으로 해지하면 위약금 없음.
핵심 규칙 — 무엇을 입력했는지가 곧 해지 방식
· 실제 입금받은 위약금 금액을 입력하고 [해지 승인] → 해지(위약금)으로 종결
· 반납된 단말기 시리얼번호를 입력하고 [해지 승인] → 해지(기기반납)으로 종결
둘 중 하나만 입력해야 하며, 둘 다 비어 있거나 둘 다 입력된 경우 저장을 막고 경고함.
  1. 목록 — 고객상태 해지대기인 건. 컬럼: 번호 · 고객명 · 제품 · 최종 산정 위약금(접수 시 산정값) · 실제 입금 위약금(입력) · 반납 시리얼번호(입력) · 처리[해지 승인].
  2. 위약금 경로 — 실제 입금액은 산정액과 다를 수 있으므로 입력값을 그대로 기록(감액 협의·부분입금 반영). 종결 시 컨텐츠 사용중단 대상으로 자동 등록.
  3. 기기반납 경로 — 입력한 시리얼번호를 4-6에서 등록된 시리얼과 대조. 불일치 시 저장을 막고 경고(오배송·타 고객 단말기 방지).
  4. 권한 — 관리자관리 · 관리자 · 매니저아웃바운드매니저 · 재무담당자재무 · 관리자.
  5. 다운로드 — [위약금 산정내역 CSV] : 최초 산정 위약금 · 할인 금액 · 최종 위약금 · 실제 입금 위약금 · 고객상태 컬럼 포함.
컨텐츠 사용중단 — CMS는 "대상 등록"까지만 위약금으로 해지 종결된 건을 컨텐츠 사용중단 대상 목록에 자동으로 올리고, 실제 차단은 시스템실에 요청해 처리함(현행과 동일). CMS가 학습 시스템을 직접 제어하지 않음.
미납으로 인한 학습 차단은 이번 범위가 아님 — 지금처럼 건별로 시스템실에 개별 요청함. 따라서 CMS에 미납 n회 자동차단 같은 규칙은 넣지 않음.
※ 현재 구글시트 학습차단리스트는 시스템실에 개별 요청한 건을 모아둔 대장이며, 위 규칙에 따라 위약금 해지분만 CMS가 자동 생성하고 나머지는 지금 방식 유지.
기기 회수 확인은 시리얼 입력 한 번으로 기기반납 건도 4-1 입고 / 4-3 수동입고처리 화면을 거치지 않음. 반납 단말기의 시리얼번호를 이 화면에 입력하는 것으로 회수 확인이 끝나고 그대로 종결됨.
위약금 부분 입금(분할)도 [해지 승인]으로 종결 가능하며, 산정액보다 적으면 확인 문구만 띄우고 진행함(차액은 미회수액으로 기록). 상세는 9-1. 위약금 산정 규칙의 "현장 자유도" 참조.
상태전이 해지대기 → (해지 승인) → 해지(위약금) 또는 해지(기기반납)

9 국내 CMS 반품접수창 (참고 템플릿)

"국내 CMS 반품접수와 동일"의 실제 기준 화면. 국내 접수창은 위저드가 아니라 하나의 긴 스크롤 페이지이며(아래 4장은 길어서 잘라 캡쳐), 위→아래로 ①접수조건 → ②위약금 정산 → ③결제·환불 → ④상담내용을 한 화면에서 작성·저장. 베트남은 청약철회/계약해지 구분이 없고, 접수 단계에서 위약금결제 · 기기반납을 고르지도 않음 — 이 창에서는 위약금 산정까지만 하고, 방식은 8번 해지대기에서 결정됨. 아래 초록 박스가 베트남 적용 포인트.

참고

9-1 위약금 산정 규칙 확정

중도해지 시 고객이 부담할 금액. 국내의 항목별 합산 방식(1회차 할인금액 · 면제 환급금 · 돈버는학습 반환금 …)을 쓰지 않고, 경과일수에 따른 정액 상한 하나로 결정함.

해지 접수 · 3-6

배송완료일 기준 정액 위약금

배송완료일로부터위약금 총액처리
14일 이내 (14일째 포함)4.000.000 ₫해지 가능
14일 초과 ~ 60일 (60일째 포함)5.000.000 ₫해지 가능
60일 초과—원칙상 중도해지 불가 — 접수는 되지만 경고 표시 + 관리자 승인이 있어야 종결
기준일 = 배송완료일 = 4-6 시리얼번호 등록일 시리얼을 등록한 날을 배송완료로 보고, 그날부터 경과일수를 센다. 시리얼 등록 전(=계약완료 전) 건은 애초에 해지 접수 대상이 아님.

계산식

최초 산정 위약금 = max(0, 위약금 총액 − 고객 기납부액)
최종 위약금     = max(0, 최초 산정 위약금 − 조정(할인))
  • 위약금 총액 — 위 표의 4.000.000 / 5.000.000 ₫. "고객이 낸 돈 포함"이라는 뜻은 이 금액이 고객이 부담할 총액 상한이라는 의미.
  • 고객 기납부액 — 선납금 + 납부한 할부금 합계(17-1 회원현황 누적납부금액과 동일 값). 감면액은 실제로 받은 돈이 아니므로 제외.
  • 기납부액이 총액을 넘는 경우 — 청구액 0으로 처리. 초과분 환불은 하지 않음(환불 프로세스 없음).
  • 미납 회차가 있어도 별도로 청구하지 않음 — 미납금은 위약금 총액에 흡수됨. 예: 월납 990.000 × 6회차 경과인데 3회차만 납부했어도, 미납 2.970.000을 따로 받지 않고 위 산식만 적용.
  • 조정(할인) — 미납담당자 · 매니저가 협의로 감액한 금액. 최초/할인/최종 3개 값을 모두 기록해 8번 CSV · 18-2 엑셀에 그대로 출력.

해지 방식별 적용

해지 방식위약금결정 시점
위약금 결제위 산식으로 산정한 최종 위약금을 입금받음. 3-6에서 실제 입금액을 입력해 종결3-6 해지대기에서 무엇을 입력했는지로 결정
기기반납위약금 없음 — 반납 시리얼번호만 확인하고 종결

60일 초과 건 처리

  1. 상담창에서 해지 접수 자체는 가능. 접수창 상단에 "배송완료 60일 초과 — 원칙상 중도해지 대상 아님" 경고를 띄우고, 예외 사유를 상담내용에 기록하게 함.
  2. 저장되면 3-6 해지대기 목록에 [60일 초과 · 관리자 승인] 뱃지가 붙음.
  3. 이 건은 관리자관리 · 관리자만 [해지 승인] 가능. 매니저 · 재무담당자는 승인 버튼을 눌러도 차단됨.

현장 자유도 — 금액은 막지 않음

산식은 기본값일 뿐, 최종 금액은 담당자가 정함 위 산식으로 최초 산정 위약금을 자동 계산해 띄우되, 조정(할인)에 상한을 두지 않음. 감액 폭이 커도 저장을 막지 않고, 대신 최초 · 할인 · 최종 3개 값을 모두 기록해 나중에 추적할 수 있게 함.
  1. 60일 초과 예외 승인 — 기준액 5.000.000 ₫를 기본값으로 띄우되 관리자가 금액을 직접 수정 가능. 0원 처리도 허용하며, 사유를 상담내용에 기록.
  2. 부분 입금(분할)도 [해지 승인]으로 종결 가능 — 3-6에서 실제 입금받은 금액을 그대로 입력하면 최종 산정액보다 적어도 종결됨. 완납을 강제하지 않음.
    단, 산정액보다 적으면 저장 전 확인 문구를 띄우고(진행은 가능), 차액을 미회수액으로 기록해 위약금 산정내역 CSV에 남김.
  3. 초과 입금도 그대로 기록 — 입력값을 그대로 저장하고 별도 환불 처리 없음.
요약: 계산은 시스템이, 결정은 사람이. 시스템은 기본값 제시 + 이력 기록만 하고, 금액 자체로 진행을 막지 않음.

회차 반영 — 자유도 높은 충당 방식 핵심

회차를 성공 / 실패 2값으로 보지 않음. 회차마다 납부액 · 감면액을 따로 쌓고, 들어온 돈을 1회차부터 순서대로 채운다. 고객이 월납부금과 다른 금액을 아무 때나 넣는 베트남 입금 방식을 그대로 담기 위한 구조.

  1. 입금 팝업 — 납부현황 영역의 [입금 등록] 버튼. 입력 항목은 입금금액 · 감면 금액 두 개(+입금일)뿐.
  2. 앞에서부터 채운다 — 저장 시 미충족 회차를 회차 번호 순서대로 채움. 한 회차를 채우고 남으면 다음 회차로 계속 넘어감. 감면액도 충당액으로 같이 잡음.
  3. 자동으로 돌면서 실패를 찍는다 — 충당이 끝나면 전 회차를 다시 훑어 경과회차 중 한 푼도 안 들어온 회차만 미납으로 표시.
  4. 일부만 냈으면 실패가 아니다 — 0 < 충당액 < 월납부금인 회차는 부분납부. 미납횟수에 넣지 않음(부족액은 미납금 합계에는 포함).
  5. 초과 입금은 다음 회차로 자동 충당 — 들어온 돈은 아직 도래하지 않은 예정 회차까지 계속 채움. 전 계약 회차를 다 채우고도 남는 금액만 선충당 잔액으로 보관하고, 채울 회차가 생기는 즉시 자동으로 충당됨(회차 건너뛰기로 회차가 늘거나, 입금 취소로 빈 회차가 생긴 때). 환불하지 않음.
  6. 회차별 개별 입금 등록 추가 — 납부현황 그리드의 각 회차 카드에 [+ 입금] 버튼. 누르면 그 회차부터 순서대로 충당하는 개별 입금 창이 열리고, 입금액은 그 회차 부족액이 기본값으로 채워짐. 초과분은 다음 회차로 이어서 충당.
  7. 회차 관리 — 약정일자 조정 · 회차 건너뛰기 추가 — 입금 등록 창 하단의 회차 관리 표에서 회차별 약정일자를 직접 수정하고 회차를 건너뛸 수 있음. 상세는 아래 표.
회차 상태조건미납횟수 집계
완납납부액 + 감면액 ≥ 월납부금제외
부분납부0 < 납부액 + 감면액 < 월납부금제외 (실패 아님)

집계 정의 미납원금 = 경과회차 부족액 합계(부분납부 부족분 포함) · 미납횟수 = 충당액 0인 경과회차 수 · 누적납부금액 = 회차별 납부액 합 · 감면/조정금액 = 회차별 감면액 합.
경과회차 정의 — 약정일 도래 기준 입금 여부와 무관하게 회차 약정일이 오늘까지 지난 회차 수. 납부 건수로 세지 않음. 약정일은 매월 10일 고정이므로 회차 n의 약정일 = 결제시작일 + (n−1)개월의 10일.

건너뛰기 해제맨 뒤에 추가됐던 회차를 회수하고 일자·총 회차·계약만료일을 원상 복구(추가된 회차에 입금이 없을 때만).
예시 전체 24회차 계약에서 2회차(약정일 21/02)를 건너뛰면 → 3회차가 31/03으로 밀리고, 이후 회차가 모두 1개월씩 순연되며, 전체 25회차가 되고 계약만료일도 1개월 연장됨.
건너뛴 회차는 미납으로 잡히지 않고, 받아야할 금액(경과회차×월납금) 계산에서도 빠짐. 입금 충당 시에도 건너뛴다.
총 청구액은 변하지 않음 — 일정만 미루는 것 건너뛴 회차는 청구액 0인 빈 회차로 남고, 실제 청구되는 회차 수는 그대로임.
예) 24회차 계약에서 1회 건너뛰면 → 회차 슬롯은 25개, 그중 청구 회차는 여전히 24개, 총 청구액 = 월납부금 × 24 (불변), 계약만료일만 1개월 뒤로.
따라서 월납부금 · 총액 · 잔여 총액은 손대지 않고, 약정일과 계약만료일만 이동함.
계약서 지급일정표에는 최초 계약 회차 수로 이미 출력되어 나갔지만, 총액과 월납부금이 그대로라 계약서 금액과 어긋나지 않음. 다만 만료일이 밀리므로 건너뛴 사유 · 처리자 · 일시를 고객 히스토리에 기록할 것.

컨텐츠 구성과 가격은 서로 무관 — 확정 같은 4종을 산 고객 A와 B의 구매가가 다를 수 있음. 따라서 패키지는 가격을 갖지 않음.
· 패키지는 영어 · 한국어 2종의 기본 구성만 등록해 두고, 실제 컨텐츠 조합은 코디가 계약 건별로 접수창에서 새로 만듦.
· 가격은 접수창에서 선납금 · 할부원금 · 할인금액 · 할부기간을 입력하면 산출되는 총액으로 정해지고, 그 총액에 매핑된 내부코드가 자동 부여됨 → ②.
  • 등록 항목 — 패키지명 · 단말기(A11 단일 · 기본 제공) · 기본 컨텐츠(6종 중 체크) · 렌탈창 노출(보임 / 숨김). 가격 · 패키지 유형 · 패키지별 내부코드 항목은 없앰.
  • 무료 제공분도 기본 컨텐츠에서 함께 체크 — 무료로 얹어 주는 컨텐츠를 따로 관리하지 않고, 계약에 들어가는 컨텐츠 전부를 접수창의 기본 컨텐츠에서 선택함. 어차피 컨텐츠 구성이 가격을 결정하지 않으므로 유·무료를 나눌 실익이 없음.
등록 패키지 관리 — [수정] + [보임/숨김] 목록에서 [수정]으로 패키지명 · 기본 컨텐츠를 고칠 수 있고, 렌탈창 노출(보임 / 숨김)은 목록에서 바로 토글해 접수창 노출만 따로 껐다 켤 수 있음.
  • 보임 — 1-2 접수창 상품명 선택에 노출.
  • 숨김 — 접수창에서 사라지되 기존 계약 건의 컨텐츠 구성 · 내부코드는 그대로 유지(과거 데이터 조회·엑셀 집계에 계속 쓰임).
  • 수정 검증 — 패키지명 필수 · 기본 컨텐츠 최소 1개.
